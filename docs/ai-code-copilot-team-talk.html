TEAM TALK / 10-15 MIN

让 AI 在正确的上下文里写代码

ai-code-copilot 是一套面向工程团队的协作纪律：先对齐需求，再锁定规格，最后编码、验证、审查、归档。

Context First, Code Follows.
Codex Claude Code Spec-driven Evidence Before Claims
开场建议：先强调这不是“多一个提示词”，而是把团队协作流程产品化。

01 / WHY

问题不是 AI 不会写代码，而是它经常不知道该写什么

直接开写

  • 需求理解靠聊天记忆
  • 变更范围不清，容易越写越多
  • 测试和验证变成事后补票
  • 下次会话重新解释一遍背景

上下文先行

  • 项目规则、领域约束先加载
  • spec / quick-card 明确边界
  • 每个 task 有验证证据
  • 经验沉淀到 knowledge，下一次自动复用
这一页的重点：AI 写代码很便宜，但修偏航、补上下文、复盘事故很贵。

02 / CORE IDEA

ai-code-copilot 把“上下文”变成项目资产

rules/ 项目架构、编码风格、业务约束、安全红线。AI 每次工作前先读规则。
changes/ 每个需求的 design-brief、spec、tasks、test-spec、log。过程可追溯。
knowledge/ 从 review 和 archive 沉淀经验。踩过的坑不靠人肉提醒。
这些内容放在 .ai_code_copilot/，建议提交到业务项目 Git。它不是缓存，是团队共享上下文。

03 / FLOW

完整流程：从想法到归档

brainstorm 对齐问题、现状、方案和风险。
propose 生成 spec、tasks、test-spec 和 log。
apply 按 task 写代码，每步验证。
review 先查需求合规，再查代码质量。
archive 把经验沉淀到 knowledge。

核心变化：AI 不再是“即时生成器”，而是沿着团队认可的流程推进。

04 / COMPLEXITY

不是所有需求都走同一套重量级流程

Quick 小改动，少于 5 个文件。生成 quick-card + log，轻量审查。
Standard 默认新需求。brainstorm → propose → apply → review。
Complex 跨模块或长周期。先 roadmap，再拆子项目分别 Standard。
默认建议：业务逻辑走 Standard，纯小修才走 Quick。

05 / GATES

两条硬门禁，挡住大多数“AI 写歪了”

No Spec / Quick Card, No Code Standard/Complex 没有确认过的 spec 不写代码。Quick 没有 quick-card 不写代码。
Evidence Before Claims 不能说“应该好了”。每个 task 完成都要展示编译、测试或可验证命令输出。
这不是为了变慢，而是为了不把“快”花在返工上。

06 / INIT

第一次接入项目，只需要初始化一次

在业务项目根目录说“初始化项目”，或执行脚本。框架会自动检测 Java / Go / Python / Frontend，并生成项目级上下文。

.ai 项目目录使用隐藏名 .ai_code_copilot/，全局安装目录仍是 ai_code_copilot/。 
bash ~/.codex/ai_code_copilot/scripts/init_project.sh --project .

git add .ai_code_copilot/
git commit -m "chore: init ai-code-copilot"

07 / GIT

为什么 .ai_code_copilot/ 要提交到 Git

提交
  • rules：团队规范和业务约束
  • changes：需求规格和执行记录
  • knowledge：项目经验库
忽略
  • .ai_code_copilot/**/*.new
  • .ai_code_copilot/**/.DS_Store
  • 团队可选忽略 .copilot-state.json

判断标准：能帮助团队复用上下文的提交；只代表本机状态或合并候选的忽略。

08 / REVIEW

Review 不是“看看代码”，而是两阶段验收

Spec Compliance 独立上下文读取 spec 或 quick-card，逐条验证实际代码是否满足目标、范围和验收条件。
Code Quality 对照 rules、安全红线和技术栈规则，检查 Critical / Important / Minor 问题。
先确认做对了，再确认写好了。

09 / ARCHIVE

每次需求结束，都让团队记忆变厚一点

log.md 记录过程决策、验证输出、review 结论、遗留问题。
knowledge/ 从 log 里提取可复用经验，下次 propose 自动按关键词加载。

这一步解决的是团队长期问题：同样的坑，不要每个新人、每个 AI 会话都重新踩。

10 / ROLLOUT

团队落地建议：先试点，不要一口气全流程铺开

第 1 周 选 1 个服务初始化，补齐 project-context 和 domain-rules。
第 2 周 选 2-3 个 Standard 需求走完整流程，保留 review 记录。
第 3 周 复盘模板、规则和知识库，形成团队默认用法。
不要先追求“自动化一切”。先让上下文、边界和证据变成默认动作。

11 / TAKEAWAY

今天希望大家带走三句话

先上下文，后代码 AI 生成能力不稀缺，准确上下文才稀缺。
先证据，后结论 编译、测试、审查输出比“我觉得没问题”可靠。
先沉淀，后复用 把规则、spec、知识提交到项目里，让团队一起受益。
试点入口：找一个真实需求，从“初始化项目”开始。
