# 通用编码规范

> 本文件只放跨语言都成立的规则。语言、框架、目录结构、测试工具等细节必须放到 `packs/<tech-stack>/rules/` 或项目级 `.ai_code_copilot/rules/`。

## 1. 命名与可读性

- 名称必须表达业务含义，避免无意义缩写、拼音或混合语义。
- 模块、函数、类、组件都应保持单一职责；难以一句话说明职责时优先拆分。
- 常量、枚举、配置项要有明确命名，禁止散落魔法值。
- 公共 API、领域对象、事件名、错误码必须保持前后一致。

## 2. 错误处理

- 不得吞掉异常或错误；必须向调用方返回可诊断的信息，或记录足够上下文后继续抛出。
- 不得用 `null`、空对象或默认值掩盖失败，除非 spec 明确允许并说明原因。
- 对外部依赖失败要有超时、重试、降级或失败传播策略，并在 spec 中写清楚。

## 3. 日志与可观测性

- 关键入口、状态变更、外部依赖调用和异常路径要有可追踪日志。
- 日志必须包含必要业务标识或 trace id，但禁止输出敏感信息。
- 新增异步、批处理、定时任务、消息消费逻辑时，必须说明失败重试和监控方式。

## 4. 接口与数据边界

- 写操作必须考虑幂等；幂等 key 来源应在 spec 中说明。
- 涉及并发、缓存、事务、状态流转时，必须说明一致性策略。
- 输入必须校验边界，输出必须保持兼容；破坏兼容性时必须在 spec 中标注。

## 5. 可维护性

- 优先复用项目现有模式和公共能力，不随意引入新依赖或新架构风格。
- 大函数、大组件、大模块要按可测试边界拆分。
- 新增复杂分支时必须补充测试或解释为什么无法自动化验证。
- 删除、迁移、重命名公共接口时必须说明影响范围和回滚方式。
